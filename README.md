# Mathmag Builders Management System (MBMS)

A construction-company ERP for Mathmag Builders Limited (Kenya), built with TypeScript throughout.

## Prerequisites

- [Node.js 20+](https://nodejs.org/) and npm 10+
- PostgreSQL 14+ (local or managed)
- Git

## First-time setup

```bash
# 1. Clone and enter the repo
git clone <repo-url>
cd mathmag-mbms

# 2. Copy environment config and fill in the values
cp .env.example .env
# Edit .env — minimum required for live use: DATABASE_URL, JWT_SECRET, MFA_ENCRYPTION_KEY

# 3. Install all dependencies (monorepo)
npm install

# 4. Set DATABASE_URL to your PostgreSQL database and provide local JWT/MFA secrets
# 5. Build and apply the database migration
npm run build
npm run db:migrate
```

## Start development servers

```bash
# Terminal 1: API (port 3001)
npm run dev:api

# Terminal 2: frontend (port 5173)
npm run dev:web
```

The Vite dev server proxies `/api` requests to the API workspace on port 3001,
so frontend requests stay same-origin during development.

- API health check: http://localhost:3001/api/health
- Web app: http://localhost:5173

## Run tests

```bash
# Unit and integration tests (Vitest) for API + shared packages
npm test

# End-to-end tests (Playwright) — web server must be running
npm run test:e2e --workspace=apps/web

# Or use the Playwright UI
npm run test:e2e:ui --workspace=apps/web
```

## Database tasks

```bash
# Build the migration runner and apply versioned PostgreSQL migrations
npm run db:migrate
```

## Environment variables

All variables are documented in `.env.example`. For a real deployment, the required variables are:

| Variable | Description |
|----------|-------------|
| `DATABASE_URL` | PostgreSQL connection string |
| `JWT_SECRET` | Shared JWT signing secret, minimum 64 characters |
| `MFA_ENCRYPTION_KEY` | AES-256 key material for MFA / secure secrets (64 hex characters) |
| `CORS_ORIGIN` | Optional frontend origin; unified Wasmer deployments use the same origin |
| `VITE_DEMO_MODE` | Set to `false` in production to disable the demo sign-in flow |
| `VITE_API_BASE_URL` | Optional browser API path; defaults to same-origin `/api` |

Everything else has a sensible default for local development.

## Deployment

### Security hardening (Step 14)

The following hardening measures are applied to the production build:

| Measure | Where |
|---------|-------|
| `Content-Security-Policy` (default-src 'self', no unsafe-eval) | `server.js`, `settings/config.toml`, `apps/web/public/_headers` |
| `X-Frame-Options: DENY` | same as above |
| `X-Content-Type-Options: nosniff` | same as above |
| `Referrer-Policy: strict-origin-when-cross-origin` | same as above |
| `Permissions-Policy` (camera/mic/geo/payment blocked) | same as above |
| Immutable cache for hashed assets, `no-store` for `index.html` | same as above |
| Build-time demo-mode opt-out (`VITE_DEMO_MODE=false`) | `apps/web/src/lib/api.ts` |
| Directory-traversal guard | `server.js` |
| No secrets in frontend bundle | `apps/web/src/vite-env.d.ts` audit |

### Wasmer Edge (primary)

```bash
# Builds the API and frontend, then deploys both behind one HTTP server
wasmer deploy
```

The root `app.yaml` and `wasmer.toml` configure one Node.js server. The root
build script compiles the API into `apps/api/dist/` and the Vite frontend into
`public/`; `/api/*` requests are handled by the API and all other client-side
routes fall back to `public/index.html`. See [WASMER_DEPLOY.md](./WASMER_DEPLOY.md)
for local smoke tests and deployment environment requirements.

### Node.js fallback server

```bash
# Build first; serves the UI and API together on port 8080 (or $PORT)
npm run build
node server.js
```

All security headers are injected by `server.js` on every response.

### Environment variables

Copy `.env.example` to `.env` and fill in the required values before running.
For Render deployment, set these in the service dashboard:

- `DATABASE_URL`
- `JWT_SECRET`
- `MFA_ENCRYPTION_KEY`
- `CORS_ORIGIN`
- `LOG_LEVEL` (optional)

For the frontend build, set:

- `VITE_DEMO_MODE=false`
- `VITE_API_BASE_URL` is optional and defaults to the same-origin `/api`.

The API applies versioned, idempotent PostgreSQL schema migrations at startup.
`npm run db:migrate` can apply them explicitly after compiling the API.

This disables the demo-only sign-in experience and points the browser at the live API.

## Important business rules

1. An enquiry is **not** a project. A project exists only after a confirmed booking.
2. One persistent project record for the whole lifecycle (never create a second one).
3. One booking → exactly one project (enforced transactionally with a unique constraint).
4. Approval, assignment and client publication are **separate** actions, each audited.
5. Approved and published versions are **immutable** — changes create new versions.
6. Authorization is enforced **server-side** on every API route and file download.
7. Clients see only **explicitly published** items for their own project.
8. Every critical action writes an **append-only audit event**.
9. Never invent missing data. Solar path = computed, wind = observed, sketch = preliminary.
10. Time zone: Africa/Nairobi · Currency: KES · Phones: +254 format.
